## 2. 身份与机构隔离

- User 是登录身份；OrganizationMembership 是机构身份；EventStaff 是指定赛事或比赛的工作授权。平台权限、机构权限和球队身份不能互相替代。
- 工作人员走机构成员及赛事分配授权；外部领队、球员走 `TeamAccessGrant`、本人参赛身份绑定及有效邀请授权，不要求先成为机构工作人员。接受球队/球员邀请不产生机构后台权限。每个动作明确允许哪条授权路径，不能把所有机构私有接口都写成“机构成员才可进入”。
- 机构范围的私有业务资源都有 `orgId`，全局身份与平台配置单独建模。服务器从可信会话取得操作者，再验证路径机构、资源归属及具体动作权限；不信任客户端传入的角色或 `orgId`。
- 同一事务内的赛事、报名、名单、场次等引用必须属于同一机构。数据库复合外键与应用查询同时约束归属；跨机构访问按不存在处理。
- 首版长期球队档案由机构维护。跨机构参赛通过明确授权导入参赛快照，不开放任意跨租户 JOIN；全平台统一球队身份不是首版前置条件。
- 平台运营人员不能因“平台管理员”身份默认读取身份证、手机号或保单。支持介入需要明确授权、最小字段和操作审计。
- 公开赛程、比分、榜单、球员展示及 OBS 使用独立 DTO 白名单，不直接序列化内部实体。未发布赛事、个人证件和保险材料不得进入公开投影。

## 3. 写入、事件与实时读取

普通编辑使用资源 `version` 做乐观并发控制。比赛写入额外要求主记分租约、幂等键和连续的比赛版本；一个时刻仅一个有效主写端。租约转移递增 `fencingToken`，旧端即使重连也不能继续写入。

比赛命令在同一事务中完成：鉴权及状态检查 → 校验租约和期望版本 → 保存追加事件 → 更新比分/统计投影 → 增加比赛版本 → 写审计及待发送事件。可采用事务 Outbox 保证提交后投递；Outbox 是后续实现方案，当前没有 worker。观众和 OBS 按单调版本消费快照/增量，发现版本缺口时重取快照，不靠消息到达顺序累加比分。

事件不直接删除或覆盖。撤销、更正追加补偿事件并引用原事件，投影统一重算受影响的数据；重复撤销被拒绝。未采集的统计字段保留 `null` 和采集模式，UI 显示“未统计”。确认赛果后才更新正式积分榜；更正已确认赛果必须重开、审计、重确认，并使受影响榜单重新计算。

## 4. 计时与断网

比赛计时保存 `period`、`remainingMs`、`running`、`anchorServerTime`、`clockVersion`。客户端根据服务器时差及锚点平滑显示，暂停和校时均产生可追溯的命令；不能每秒写一次数据库，也不能让 OBS 的本地计时成为权威。

工作台断网时可保存本机待同步操作，但界面必须显示“未同步”，不得把它视为已确认赛果。重连先读取最新快照、重新取得有效租约，再按命令 ID 核对已接受项。基线未变化且业务校验通过才能顺序补交；有其他写端、版本冲突或赛果已确认时进入人工核对，不采用最后写入覆盖。计时冲突需确认恢复锚点，不能悄悄沿用旧时钟。离线队列不保存证件与保单。

比赛倒计时、事件发生的服务器时间、设备采集时间及录像媒体时间分开存储。视频对齐采用媒体 session 和 PTS/偏移锚点，暂停、断流、重新录制都不能用一条简单时间差永久推算。

## 5. 安全与运行边界

会话、动作对应的工作人员或参赛者授权、机构与赛事资源归属每次请求验证，包含幂等重放。文件上传走受控授权，下载重新鉴权；敏感材料使用独立访问策略。日志不记录密钥、完整身份证、保单内容和直播推流密钥。

本地、测试、生产分离。可观测项至少包含请求 ID、事件 ID、比赛版本、同步延迟、失败队列、授权拒绝和更正记录；运行告警阈值在上线准备阶段确认。付款、退款、套餐扣量和 Migration 必须经过各自设计与授权，首版不因 UI 出现入口就自动启用。
