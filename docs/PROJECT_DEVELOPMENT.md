## 2. 定位与商业目标

品牌：**小城市篮球**。宣传语：**小城市，也有大主场。**

为赛事公司、协会、场馆和长期主办方提供可重复使用的篮球办赛工具。球员、领队和观众是参与者；付费对象优先为机构。青锋杯仅作试点，球队数、场次数和赛制都不能写死为某一届规则。

优先完成“创建赛事→报名审核→抽签排赛→现场记分→赛果确认→榜单与赛后交付”。前期按届服务，后续视复购增加年费；视频服务及人工支持单列成本。定价、退款条款和具体套餐尚未确定，不据此开发自动扣费或资金托管。

## 4. 总体技术方向

采用 TypeScript 为主：Taro + React 小程序，React + Vite 机构后台及现场端，NestJS + PostgreSQL 后端；先做模块化单体。P01 前端依赖已核验安装并锁定于 main 代码，运行说明见[DEVELOPMENT](DEVELOPMENT.md)。P02已用pg参数化SQL及真实PostgreSQL完成验收；云供应商、微信账号及生产域名尚未配置为已验收服务。

目标目录见[架构](ARCHITECTURE.md)。main 已建立 `apps/admin`、`apps/api`、`packages/contracts`、数据库迁移与验证脚本；其余应用按阶段实施。跨端实际复用后再提取共享 UI。

## 5. 必须保持的业务原则

1. 多机构资源归属与权限在服务端判断；平台客服或运营不默认获得身份证和保单访问权。
2. 长期球队和单届报名名单分离，历史名单不因后来人员变动而改变。
3. 赛制、积分与排名、休息间隔等使用版本化赛事规则；不满足排赛条件时报告冲突，不能静默放宽硬约束。
4. 同一比赛只允许有效主记分者写入；事件具备幂等键、版本及更正链。P05-A断网停止新写，未知提交原包仅在内存保留并核对收据，不能宣称可靠离线；冲突不能用最后写入覆盖。
5. 基础模式不伪造球员高级统计；P05-A已实现独立确认／重开。P05-B按显式锁定规则汇总当前有效确认，重开整场退出、重确认只计最新一次，同分保留共享名次；该分支仍待验收，FINAL或全部确认都不自动转赛事COMPLETED。
6. 比赛倒计时、服务器时间及录像时间分别建模；OBS 离线不影响记分。
7. 外购保险凭证可以提交审核；上传成功不等于保单有效或保险责任已确认。
8. 套餐服务费、参赛费、保证金、视频用量是不同业务，不用一张含糊的订单表混算。

公开观赛须单独启用，使用独立公开ID和每次发布专用teamKey；匿名无会话，撤销后后续读取404，再启用全新标识。未准备比分／时钟为null，不伪造0；公开数据不含名单、人员授权、写凭据和内部身份ID。

上述保险文件、可靠离线和内容交付仍有后续范围，P05-B排名／观赛仍待验收。P03-A已交付Web报名冻结，P04-A已交付2–32队单循环及一次发布，P05-A已交付基础在线记分和独立确认；这些首卡不等于完整P03／P04／P05或OBS已完成。

## 8. 多 AI 使用顺序

新会话先读根目录 `AGENTS.md` 和动态状态，只读本任务需要的规范。Claude Code 入口为根目录 `CLAUDE.md`；[实施模板](agent-prompts/CLAUDE_P01.md)和[审查模板](agent-prompts/CODEX_REVIEW.md)用于后续明确启动的任务。

“实时更新”采用工作事件触发：开工、检查点、受阻、接口变化、验证完成、交接和整合时更新。不是已部署的自动文档机器人；没有 AI 运行或没有仓库写入连接时，远端不会自行变化。无同步权限或连接时必须将状态标为“仅本地，未同步”，并交付未丢失的记录。
