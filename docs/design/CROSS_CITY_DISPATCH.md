# 跨城自动派单设计

状态：待实施设计，非已开发或已测试功能。基线：`main@ebc391e8bd0ec24c3301f64d6ae2f395245701cb`；设计日期：2026-11-01（Asia/Shanghai）。

## 1. 产品边界与复用

自动派单指用户明确启用后，向合格人员发出有限批次的服务邀请；服务方可以拒绝，系统不能替其接受。先开放已核验的裁判、记录、摄影、直播等 X12 人员服务。球场、球队约赛和 C06 成人球员邀约不直接套用此状态机；医疗类须独立资质和服务范围门槛，默认关闭。

复用[本地服务](../../apps/api/src/local-services-service.ts)、[本地领域](../../apps/api/src/local-services-domain.ts)、[控制器](../../apps/api/src/local-services-controller.ts)、[C06 日历](../../apps/api/src/player-booking/service.ts)、[交易日历钩子](../../apps/api/src/trade-source-hooks.ts)和 E04 交易。当前 X12 已有覆盖范围、人员档期、10 分钟预约待确认期、请求/确认/取消与资源排斥；没有本设计的跨城任务、批次、报价接受暂占和差旅审核。不得把旧 DTO 的支付占位值解读为没有 E04 交易代码。

全国可浏览不代表服务方全国履约。只有客户主动选择“允许跨城邀请”，服务方主动启用指定城市/距离/岗位/时间段的跨城接单，且目的地属于已审核覆盖地区，才可进入候选。跨城开关不能自动扩展审核覆盖范围。首版是规则引擎、同一数据库与后台任务，不新增机器学习或微服务。

## 2. 主要流程与 UI

客户创建需求并确定总预算 → 审阅跨城费用和有限邀请范围 → 规则过滤并分批邀请 → 一位服务方确认可接并提交明细报价 → 原子选中并暂占其日历 → 客户复核全部条件 → 转入真实 X12 订单 → 服务方在原订单再次确认履约 → 按 E04 门槛付款及履约。

“接受邀请”在首版意味着接受报价协商，不冒充已确认订单；真实订单确认沿用源模块权限和命令。自动补人不能改变已确认订单的履约方。

| 页面/使用者 | 字段与操作 | 异常状态 |
| --- | --- | --- |
| 创建需求/客户 | 服务类型、人数（首版固定 1 人）、组织/赛事、真实城市地址、报到/服务结束、本地时区、资质、费用上限、最晚确认时间；预览并启用跨城 | 定位可拒绝；地点必须人工确认；多人组合转人工，不暗中拆单超预算；无供给只登记 |
| 派单设置/客户 | 邀请地区、最大批次/人数、邀请截止、交通/住宿分项上限和总上限；暂停/关闭 | 首版每批最多 3 人、最多 3 批，均为可版本化运营参数；不得无限扩散或自动加预算 |
| 跨城偏好/服务方 | 已审核覆盖地区内的可接城市、出发城市、工作日历、休息/交通缓冲、通知时段、单日邀请上限；启停 | 保存偏好不等于修改供给审核范围；关闭后停止新邀约 |
| 邀请详情/服务方 | 城市、岗位、服务时间、预算、已授权的场地摘要；接受并报价/拒绝/稍后 | 报价含服务费、交通方式/费用、住宿、平台费用、到达时间和版本；已过期/被抢先接受显示失效 |
| 报价确认/客户 | 人员与资质、服务/交通/住宿/平台费用、总额、路线核实状态、退改条款、失效倒计时；确认并转预约/拒绝 | 未知项目不能显示 0 元；超限、交通未核实、条款变化禁确认；无扣款授权不收费 |
| 任务与订单/双方 | 批次进度、候选状态、真实订单入口、失败原因、改期/取消/转人工 | 响应未知显示“结果确认中”并查回执；无候选可暂停、调整需求或转人工 |

沿用蓝橙品牌、手机底部主操作、44px 触控区和 320/390/430px 响应式。通知只提示城市、岗位、站内入口，不含客户电话、精确地址或私人名单。精确服务地址仅向已被授权且需要核对行程的候选披露，并记录访问；拒绝/失效后收回后续访问。

## 3. 路程、费用与状态

时间以 UTC timestamptz 存储，另存服务地 IANA 时区用于展示和输入校验。首版只开放中国大陆，界面明确北京时间（Asia/Shanghai）；未知时区或未来夏令时歧义必须明确偏移量后才能提交。地图坐标系遵循 X12 GCJ02，不能拿坐标差或直线距离当真实交通耗时。

候选须通过当前公开/接单许可、资质有效期、组织状态、审核覆盖、档期和预算硬过滤。相邻订单地点、出发/返回、休息及现有服务缓冲共同决定可行区间。只知道城市、无法取得路线或班次时标 `TRAVEL_UNVERIFIED`，停止自动选中；可由服务方提交可核验交通方案及运营复核后进入新报价版本。人工复核也不能把“未知”改成零时长。没有现实到达余量就拒绝，不承诺全国即时供给。

费用统一整数分/CNY。报价冻结服务、交通、住宿、平台费用、应付总额及各方承担项，分别不得超过客户明确上限；现有 C06/E04 计费公式不在此改变。差旅变动、加班或另加岗位必须提出新报价并获得客户再次确认，禁止默认补扣。支付、退款、结算沿用 E04，不建设钱包或另记一套资金余额。

任务：`DRAFT → SEARCHING → INVITING → REVIEWING → SOURCE_REQUESTED → SOURCE_CONFIRMED`；无候选进入 `NEEDS_MANUAL`，客户可关闭为 `CANCELLED`，到期为 `EXPIRED`。暂停是明确阻止下一批邀请的状态，不能暂停已进入源订单的义务。报价拒绝/过期释放暂占后可回 SEARCHING，仍受剩余批次数与客户许可限制。

邀请：`PENDING → ACCEPTED_HELD / DECLINED / EXPIRED / SUPERSEDED`。只有一个当前赢家；选中后其它邀请 SUPERSEDED，不能后来接受旧邀请。客户确认后 `CONVERTED`；拒绝/服务方撤回/到期则 RELEASED。候补只是排序建议，不保留有效接受权和库存；补位必须新批次、新邀请、新报价。任务响应未知属于 UI/回执状态，不能当作业务失败创建替代任务。

## 4. 表、共享库存与原子边界

拟议新增，不表示已有：

| 表 | 字段和约束 |
| --- | --- |
| dispatch_requests | owner/org、listing_kind、service_region、时段、范围、预算、rule_version、expires_at、version、当前赢家、source_ref；首版每任务只允许一个岗位一人 |
| dispatch_batches | request_id、batch_no、candidate_snapshot、截止时间；request_id+batch_no 唯一，CAS 限制总批数 |
| dispatch_offers | request_id、batch_id、provider_id、listing_id/version、quote/version/hash、expires_at、status；批次+人员唯一，避免同人多 listing 重复邀约 |
| dispatch_holds | offer_id 唯一、provider_user_id、服务/差旅占用区间、expires_at、status；每任务至多一个 ACTIVE；源转换引用唯一 |
| dispatch_commands / outbox | actor+commandId 唯一、payload_hash、回执；event+request+version+recipient 唯一，队列重复投递不重复发送 |

PENDING 邀请不锁库存，否则群发就会占满服务方档期。服务方接受时，在一个事务内重验权限、报价、服务范围、路线与时间，CAS 选中赢家并创建短时暂占；同时接受的其他人得到“已有人员进入确认”。建议确认窗口 10 分钟，不能晚于报到准备截止，实际期限以数据库时间计算并展示；对外最终值由版本化配置确定。

暂占必须接入现有 `local_resource_reservations`，不能只在新表中检查：最小方案为该表增加可空 dispatch_offer_id，扩展所有者“一且仅一”约束和外键，用相同 `user:<provider_user_id>` 资源键记录服务加差旅保护区间。同步扩展 X12 过期释放与 C06/X12 冲突触发器，确保球员角色和工作人员角色使用同一自然人仍互斥；报价未核实之前不得写假区间。实施时检查实际约束/触发器，迁移脚本需要并发证明。

锁序：操作者/服务任务授权 → 一次收集并按 id 排序锁所有 org_schedule_mutex → x12_calendar_lock → 既有配额/命令锁及必要的 C06 profile 排序锁 → 源/任务/offer 行固定顺序。后台选批、接受、过期、转单、取消都遵守同一序列，禁止先锁任务再取日历。持锁后发现新组织关系就中止重试，不补取反序锁。

客户确认事务内重验源 listing/slot、报价版本、赢家、资格、许可、差旅、库存和 E04 适用门槛；释放暂占与创建 X12 REQUESTED 订单在同一事务内完成，并写 source_ref/回执/outbox。通过抽取同事务内部命令复用源逻辑，不串联外部 HTTP 造成中间空窗；转单失败则完整回滚暂占。临时派单锁转为订单锁后仍须保留差旅保护区间（关联源订单的扩展资源预约），直至源取消/改期按原子流程处理。不能只保留服务时段导致接下一单来不及赶场。

同键同载荷回放，异载荷 409；不在数据库事务内调用地图、消息或支付外部接口。未知外部结果先查单/查回执，使用唯一事件键恢复，禁止重发收费。源创建后服务方未在原期限内确认则走源 EXPIRED，释放服务及差旅资源；原子转单并不等于确认/付款成功。

## 5. 异常、API、迁移与权限

取消前展示当前源订单阶段、可能退款和差旅处理；确认订单有取消/纠纷责任时只能走源规则。改期先核验并暂占新完整区间，双方批准后事务交换；失败保留旧安排。不得先释放旧单再尝试新单。订单取消、人员失联或交通异常触发人工升级，替换人员需要客户重新确认，不能偷偷改变 source_ref。投诉期间不自动完成结算。

以下 API 均为拟议、未实现：`POST /v1/dispatch/requests`；`GET /v1/dispatch/requests/:id`；`POST /v1/dispatch/requests/:id/commands`（START/PAUSE/RESUME/CANCEL/CONFIRM_QUOTE/REJECT_QUOTE）；`GET /v1/dispatch/offers/mine`；`POST /v1/dispatch/offers/:id/commands`（ACCEPT_WITH_QUOTE/DECLINE/WITHDRAW）；`GET /v1/dispatch/receipts/:commandId`。命令带 expectedVersion、commandId；客户端不得写赢家、接收人权限或已支付标志。

最小迁移在 042 之后与其他设计协调新编号：增任务/批次/报价/暂占/回执表，扩展资源所有者与跨模块冲突检查、订单差旅保护关联，再增加默认关闭的地区/类型开关。历史订单不自动变成跨城订单，历史服务方不默认授权全国派单；不回写旧账单或退改条款。先在测试环境核验排斥约束、过期清理和恢复，再逐城市启用。

参与者只能读己方任务/报价；城市运营只能在城市+机构+操作授权内处理，跨机构介入需原因和审计。日志不写完整路线、身份证、电话。精确路线按最小必要期限保存，订单后仅保留履约和争议需要的授权证据。

恢复进入 quarantine：关闭选批、接单、转单、outbox 和自动收费；核对有效暂占与源订单、支付状态、报价期限及权限后解隔离。外部已发送通知不可撤回，但过期链接服务端必须拒绝；原订单未知时挂起，不重建替代订单。

## 6. 验收与拆包

以下为待执行验收，不能标记已通过：

1. 客户或服务方未明确开启跨城时，不生成跨城邀请。
2. 已开启但目的地不在审核覆盖范围仍排除；医疗默认门槛不被绕过。
3. 三批上限、每批人数与通知限额在重复 worker/并发下仍成立。
4. PENDING 群发不占库存；同人多个 listing 只收到一个本批邀请。
5. 同一任务两人同时接受，只有一个 ACTIVE 暂占和赢家。
6. 同人并行接受两项冲突服务，或已有 C06/X12 预约时只能一个成功。
7. 路线未知、前后订单地点未知或时间不足禁止自动放行；人工核验留证据。
8. 服务加交通住宿总额/任一分项超上限，客户确认被拒绝。
9. 客户看到的报价变更后，旧版本确认失败且不收费。
10. 接受邀请和客户确认不伪造源订单 CONFIRMED；源服务方权限仍校验。
11. 暂占转单无锁位空窗；故障回滚不丢暂占，也不残留双重订单。
12. 转单后差旅时间仍排斥下一笔 C06/X12 冲突预约。
13. 报价到期、撤回、客户确认并发只有一个合法结果；时间以数据库为准。
14. 网络响应丢失及重复 worker/支付通知不会重复邀约、扣款或落单。
15. 改期失败保留旧锁；已确认订单不能自动换人或绕过退款/纠纷。
16. UTC 存储与北京时间往返一致；未知时区不被当本地零偏移。
17. 无权用户/城市运营不能读取私有报价、路线和联系方式。
18. 恢复备份后不补发旧邀请；未知源单/支付挂起并由核验流程恢复。

拆包：D1 跨城双侧许可、费用与路线核验契约；D2 共享库存迁移和跨模块并发测试；D3 有限批次/幂等 worker；D4 报价/暂占/客户审阅 UI；D5 原事务转单、差旅保护及 E04 对接；D6 取消改期/人工接管/恢复演练。D2 是 D3–D5 的上线前置，D5 依赖原源命令可同事务复用与收费门槛；未取得真实路线能力时可做人工报价协商，但自动派单确认保持关闭。上线以实际测试证据和小范围真实供给验证为准。
