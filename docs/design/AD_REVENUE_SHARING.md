# 广告与赞助收入分成设计

状态：设计已完成；广告订单、多方结算模型及联调未开发。基线：`main@ebc391e8bd0ec24c3301f64d6ae2f395245701cb`；核验日期：2026-11-01。

## 1. 现状与首版决策

`sponsorship-service.ts` 已支持赞助稿件、区域/赛事定向、审核、发布撤销、客户端曝光去重；`governance.d.ts` 已有 `DRAFT/SUBMITTED/APPROVED/REJECTED/WITHDRAWN` 与“广告／赞助”标签。`reportedImpressions` 明确不等于独立人数、真实观看或结算凭证。新设计新增商业合同、实收、履约确认和多方分配，不把投放审核当财务审批。

现有 `trade-provider/runtime/domain/service` 已有组织商户绑定、支付/退款/分账/回退及历史商户路由，但交易来源仅 `ENTRY_FEE/ENTRY_DEPOSIT/LOCAL_BOOKING/PLAYER_APPEARANCE`。`trade-wechat-settlement.ts` 为普通商户、单接收方分账，并固定 `unfreeze_unsplit:true`；不能循环调用它拼出多人分账。新建广告来源须覆盖契约、校验、计价、退款、权限、恢复、测试；新批次适配器独立启用，旧交易行为不隐式改变。

首版采用人民币固定价赞助订单，购买明确赛事/地区的展示档期及约定权益。一个订单对应一个收款服务主体、一份冻结合同、一笔原渠道付款、一次最终分成批次；履约周期必须落在实际渠道可分账时限内。长期合同拆成独立履约与支付周期，不能靠后台延长微信冻结期。支持平台、组织、场馆等经审核商户接收方；个人接收方、国际分账、钱包、储值、自动拍卖暂不做。CPM/CPC 待独立计量、防作弊、账务及争议标准落地后另开版本。

## 2. 主体、合同和业务流程

广告主与实际提供广告服务的主体签约，其经批准商户号收款；不能默认平台替所有组织统一收款。接收方是有合同依据的机构及其已开通接收/回退能力的商户号，服务端登记所属组织、受益角色、有效期、证据及审核人。平台若参与分成也必须是合法受益主体。税费、发票、服务责任另经财务确认，支付分账不自动解决这些问题。

合同版本固定：广告主、服务主体/商户、投放资源与日期、交付验收、固定总价、退款条件、付款周期、可扣除费用、分配基数、接收方及整数基点、留存份额、取消/补投/争议规则、凭证要求。比例合计 10000 基点；签署后不可原地改价/改收款人。变更新版本用于未来订单；已付订单只通过有依据的退款或调整单处理，不重写原合同。

流程：合同草稿 → 商业/财务独立审核 → 双方确认 → 广告主付款 → 内容审核和排期发布 → 履约证据及广告主验收/争议 → 到结算条件 → 计算批次 → 分级审批 → 渠道分账 → 逐接收方核对 → 账单归档。未付款不视为实收；内容审核通过不保证库存可售，资源档期冲突需在签约/付款前校验。既有免费或历史赞助稿可继续展示，但不自动生成付款及收益。

组织成员按合同/投放权限操作；城市运营的 `SPONSOR_REVIEW` 只授权内容审核，不自动获得财务权限。普通批次至少一名独立财务审批；达到配置的金额阈值、首笔接收方、重大退款/人工调整须第二名独立复核。阈值由财务配置版本化，不在前端写死；提议人不得自批，执行 worker 只消费有效审批快照。

## 4. 金额计算与渠道约束

全部使用整数分与整数基点，禁止浮点金额。订单锁内重算：`P = 已核验实收 - 已退及已批准/处理中的退款保留 - 合同约定且已核验的费用 - 争议保留`，P 不得为负；首版存在未决退款、分账/回退或争议时不生成最终批次。履约未验收不把暂收款转换为可结款。费用不明时阻断最终结算，不能虚填 0；固定赞助首版不使用复杂多级费用瀑布。

各方先算 `floor(P × 基点 / 10000)`，尾差按小数余数从大到小补一分，同余按冻结的受益方 ID 排序，保证合计等于 P。收款主体留存不作为外部分账请求。待批、处理中、UNKNOWN、已成功未回退明细均占用原单可分额度；同一原单共享锁，退款与结算不可并发超用。

例：已核验实收 10103 分，合同允许扣除且账单确认手续费 100 分，P=10003 分；收款主体/运营/场馆/内容方比例 70%/15%/10%/5%。原值为 7002.10/1500.45/1000.30/500.15 分，取整总计 10002，尾差一分给运营，最终 7002/1501/1000/500，总和 10003，外部分账 3001 分。比例只是业务示例；假设该商户审核通过的渠道上限为付款额 30%，渠道上限为 3030 分，本例满足。实际必须读取/核验商户配置，不能把 30% 写成全国通用许可。

普通商户官方接口要求支付下单带分账标记，分账按金额执行、异步核实；当前文档上限为每笔订单最多 50 次请求、每次最多 50 个接收方。首版产品主动限制至最多 10 个外部商户，一次最终批次；超限拆合同周期而非绕过渠道。新适配器一次提交多接收方且先不解冻余款，逐项核对后单独发完结请求；部分失败保持 `PARTIAL`，只查询/人工处理失败部分，不能重发已成功明细。全部终态及额度核对后才解冻余款；争议阻断完结。若最终确认不可继续分账，保留应付差异工单，不能换成私转按钮。

## 5. 状态、退款与坏账

| 对象 | 状态路径 | 不确定性规则 |
| --- | --- | --- |
| 合同 | `DRAFT → IN_REVIEW → SIGNED → CLOSED`；可驳回/终止 | 版本不可覆盖，终止不抹去历史收款 |
| 订单 | `WAITING_PAYMENT → PAID → DELIVERING → ACCEPTED → CLOSED` | 争议/取消分别记录；支付事实独立保存 |
| 结算批次 | `DRAFT → IN_REVIEW → APPROVED → PROCESSING → SUCCEEDED/PARTIAL` | `UNKNOWN` 查原批次号；审批后来源变化退回重审 |
| 明细/回退 | `PENDING/PROCESSING/UNKNOWN/SUCCEEDED/FAILED` | 已成功分账仅凭渠道成功回退减少净额 |

退款先确定合同退款义务，再核算资金：未分账可原路退款；已分账按冻结的退款分摊算法对原成功明细生成回退。分摊先调整合同应付：未成功分账的份额只减少应付/释放原订单保留，不发渠道回退；UNKNOWN 必须先查证。累计回退不得超过原明细，累计退款不得超过实收。不得用未到账回退抵消退款义务，退款与分账回退是独立事实。原渠道允许商户自有可用资金先行退款时，须独立授权并记录垫付与追偿，不能隐式扣其他订单资金或假装已回收。

退款不能反复对剩余池使用最大余数法，否则某些尾差组合会要求已回退方“补收一分”。首版冻结一个单调的比例退款序列：原分配金额为 `A_i`，已分配到该方的退款份额为 `r_i`；每新增一分，选 `(r_i+1)/A_i` 最小且 `r_i<A_i` 的一方，平手按冻结 ID；用整数交叉相乘比较。以累计池减少额取序列前缀，再减此前已确认/保留回退；生产可批量求阈值，结果必须与逐分参考一致。这样不会负回退、超回退，也不受分几次申请影响。

接上例，退款1001分且已核验手续费仍为100分，池减少1001分；上述算法分配收款方701、运营150、场馆100、内容方50，合计1001。收款方承担701，外部回退300。手续费变化时财务先确认池减少额和收款方费用差额；全部退款最多收回原分配金额，额外费用责任按合同处理，不靠向受益方超额回退解决；已回退资金不再次分账。

接收方余额不足、未授权、超过时限或已注销导致回退失败时，建立 `RECOVERY_REQUIRED` 工单，显示对广告主退款进度及对受益方追偿余额；暂停相关未决订单新分账。财务按合同决定追偿、获批垫付或坏账核销，核销须双人审批和凭证，只影响内部应收，不伪造渠道回退成功。不可跨组织抵扣或新增钱包余额。

## 6. 候选实体及拟议 API

复用 campaign/publication/impression 和交易支付/退款事实。候选新增：`sponsor_contract_versions`、`sponsor_orders`、`sponsor_deliveries`、`sponsor_beneficiary_snapshots`、`sponsor_settlement_batches/items`、`sponsor_recovery_cases`。审批复用统一审计能力但建立明确财务动作。交易来源新增候选 `SPONSOR_ORDER`；名称在实施时统一，不冒称现有类型。

归属约束：合同、订单、交付、结算及追偿均以 `contractOwnerOrgId`（数据库沿用归属 `org_id`）作为收款服务主体的权限范围，业务外键校验同一归属组织。受益快照单独记录 `beneficiaryOrgId`、关系授权版本及原接收商户号；可在核验合同、身份、渠道关系与双方授权后跨组织接收，不要求受益机构等于合同归属机构。跨组织关联必须经专用受益关系校验，不能放松所有业务外键或把受益方加入收款组织。

受益方仅只读自身明细、回退/追偿与相关脱敏凭证，不能读取其他受益方账号、广告主身份或审批收款方批次。合同签署快照、交易主体及接收方账户不可变；原渠道交易号/批次号/回退号唯一；原单净分账和保留额不得超容量；明细金额非负且与快照复算一致。凭证记录合同哈希、交付材料、审批人、原交易/分账明细/退款/回退号、账单摘要及差异处理，文件私有并审计读取。财务台账是应收应付及渠道事实记录，不是可充值可转出的账户。

## 7. 迁移、运维与实施拆包

迁移在 001–042 后统一分配编号；现有赞助数据不回填实收和收益。新增来源需通过全部消费方及余额不变量回归。默认关闭新广告收费/分账，按组织灰度；旧商户配置保留原主体，不能换 key 指向另一个商户。关闭新单后仍保留原号查询、退款和回退。恢复沿用 `RESTORE_QUARANTINE`，先比对原渠道事实、保留额及合同快照，禁止恢复后自动重打款。

监控：待付与实收分离、未验收实收、可结/保留/已分金额、UNKNOWN 年龄、部分失败、回退失败和待追偿、账单差异、冻结期限及回退期限临近。当前普通商户文档说明通常 30 天自动解冻、回退存在 180 天限制；生产须结合实际账号/API确认时间口径，按每单到期时间预警，不能套用平台收付通等其他模式。

拆包：①固定价合同/主体/交付与 UI；②新增交易来源、金额计算/不可变快照；③多接收方适配器、完结/查询/回退；④审批、追偿、对账恢复；⑤真实账号受控小额闭环和灰度。前两包可用沙箱推进；收款资质、接收授权、上限、结算/退款责任、发票税务规则及正式账号未确认时，不开放实款入口。

## 8. 可测试验收

1. 历史曝光数再大也不能生成实收、可结款或自动分账。
2. 未签合同、未审核主体、未开通接收/回退能力均禁止新收费分账。
3. 未授权 A 组织不能查询/审批 B 组织财务；获准跨组织受益方仅可读己方明细，不能读其他方账号或审批批次；内容审核权限不能审批分账。
4. 签后改比例/接收人产生新版本，已付订单仍绑定原合同。
5. 未验收、争议、未决退款及未知费用均不能生成最终可执行批次。
6. 示例 10003 分精确得出 7002/1501/1000/500；任意有效分值计算总和恒等于 P。
7. 退款示例得出 701/150/100/50，连续部分退款与一次累计申请一致；尾差序列不会产生负回退。
8. 超商户实际比例、渠道余额、接收方数或时限时拒绝执行，不偷偷压低合同应付。
9. 提议人自批、缺第二审核、快照变化后旧审批执行均失败。
10. 并发结算和退款在同一原单下不能超分、超退或重复保留。
11. 一个接收方成功另一方失败时逐项展示，重查不重复给成功方打款。
12. 分账超时、worker 崩溃、回调重放只按原批次查证；未全部核对不解冻余款。
13. 回退失败不展示退款完成；超额/重复回退被阻断，待追偿及垫付分别留痕。
14. 商户迁移与恢复隔离不改变旧单主体、不重复分账；关开关后仍可核对历史事实。
15. 实际小额付款、多接收方分账、部分退款/回退及账单核对全部通过才申请生产启用。
