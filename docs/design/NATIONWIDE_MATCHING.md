# 全国自动撮合设计

状态：待实施设计，非已开发或已测试功能。基线：`main@ebc391e8bd0ec24c3301f64d6ae2f395245701cb`；设计日期：2026-11-01（Asia/Shanghai）。

## 1. 目标与现有边界

全国范围内根据明确需求生成可解释的候选建议，帮助用户发起有权限的意向联系。全国可浏览不代表全国有可履约供给；无供给时显示真实缺口并允许保存需求。第一版采用模块化单体内的规则引擎和数据库任务，不引入机器学习、新微服务或付费排名。

依据：[全国需求](../NATIONWIDE_LOCAL_REQUIREMENTS.md)、[本地服务](../../apps/api/src/local-services-service.ts)、[C06 球员邀约](../../apps/api/src/player-booking/service.ts)、[球员领域限制](../../apps/api/src/player-booking/domain.ts)、[本地契约](../../packages/contracts/local-services.d.ts)。当前 X12 支持已审核供给、档期、预约和双方约赛，C06 有成人档案、档期与报价校验；尚无本设计的全国撮合任务、评分和意向状态机。E04 已有独立交易链，旧 DTO 的 `NOT_ENABLED/UNAVAILABLE` 字段不能作为交易能力不存在的依据。

三类需求严格分型：

| 类型 | 必填与资格 | 最终业务来源 |
| --- | --- | --- |
| TEAM_MATCHUP 球队约赛 | 有管理权限的球队、实际比赛城市、时间窗、规则/人数、年龄组；需求阶段场地可明确标“待定”，免费约赛不要求预算 | X12 local_matchups；最终转约赛时必须提供本人已确认的未来球场预约 |
| ADULT_PLAYER 成人球员 | 有权邀约的组织/球队、岗位、场次与报到时间、预算；现有 C06 仅 18+ | C06 booking orders/appearances；收费沿用 E04 开放门槛 |
| STAFF_SERVICE 工作人员 | 裁判、记录、直播、摄影或医疗等明确服务类型、人数、实际地址、时段、资质、预算 | X12 local_bookings；跨城自动邀约另见[派单设计](CROSS_CITY_DISPATCH.md) |

首版不把青少年纳入成人球员付费邀约。青少年球队相关需求必须经现有赛事年龄、监护授权和名单可见性校验；未建立该能力时拒绝发布该类型，不以“已有监护人”替代业务资格。场馆是明确地点的资源查询，不作为可跨城流动人员排名。

## 2. 用户流程与页面

流程：选择需求类型 → 填写实际服务地点和条件 → 审阅公开字段与搜索范围 → 生成候选 → 比较推荐理由 → 主动发送意向 → 对方确认意向 → 进入原业务预约流程。自动搜索不自动发消息、下单、扣款或改变参赛资格。

| 页面/入口 | 字段与主操作 | 异常与恢复 |
| --- | --- | --- |
| 同城/球队“找合适的人或球队” | 类型、组织/球队、城市/区县、日期、报到/结束时间、岗位/人数、预算上限、明确允许的地区；保存草稿/开始匹配 | 无管理权禁止提交；手动选城可完整使用；实际地点独立于浏览城市 |
| 需求审阅页 | 对外摘要、仅候选可见内容、截至时间、范围与通知选择；确认发布 | 付费类型缺预算，或任意类型缺时段、资格、许可范围时定位错误字段；免费约赛无需预算；不默认公开联系人和精确地址 |
| 候选结果页 | 类型、服务地区、公开资质、可用时间、已确认报价/待报价、3 条匹配理由、排序说明；查看/比较/发意向 | 无供给、仅部分满足、资料变化、已停用、过期分别显示；扩大范围须主动确认 |
| 意向详情页 | 双方需求摘要、履约边界、当前报价版本、失效时间；接受/拒绝/撤回/进入预约 | 明示“意向确认不等于预约成功”；条件变更撤销旧确认并重新审阅 |
| 我的需求/运营诊断 | 需求状态、各岗位总数/可用名额/已转单人数、已联系人数、到期时间、暂停/关闭/重新搜索；授权运营仅查看过滤原因汇总 | 已转订单终止后提示“是否重新开放此名额”，默认不补位；网络重试查回执；恢复隔离不补发旧邀请 |

手机适配 320/390/430px，复用深蓝 `#123C73`、橙 `#F28C28` 与项目组件；触控区至少 44px。返回保留筛选与滚动位置。预算拆分服务、交通、住宿、平台费用；未确认项目显示“待报价”，不显示为 0 元。价格非筛选必需的免费约赛显示“不涉及服务收费”。

## 3. 候选资格与评分

先执行硬过滤，再排序。硬过滤包括：账号/组织有效；当前公开发现许可和对应联系许可；对象审批状态；有权操作该球队；年龄/监护适用规则；服务资质有效至履约结束；服务地点属于已核验覆盖范围；明确跨城许可；档期及既有缓冲不冲突；确定报价不超过预算；需求类型与人数/职位一致。报价未知者仅进入独立“需报价”区，不宣称预算匹配；路程不可计算者不得标为可准时到场。

规则 `match-rules-v1` 仅在合格候选中排序：时段适配 35%、预算适配 25%、已核实出行适配 20%、有证据的履约记录 20%。各维四舍五入至 0–100 整数，计算如下：

| 维度 | 确定性公式及输入 |
| --- | --- |
| 时间 Sₜ | 需求填写偏好开始 p、可接受开始区间 [a,b]；从完整覆盖服务时长的合格候选时段中取离 p 最近的 s，`100×max(0,1−abs(s−p)/max(p−a,b−p))`。a=b=p 时合格即 100；无有效档期是硬拒绝，不是缺分 |
| 预算 Sᵦ | B 为该岗位席位分配上限，P 为该席位当前确定的含交通/住宿/平台费用总价；B>0 时 `100×(B−P)/B`，P>B 已硬拒绝；B=P=0 时 100。未知 P 缺分且仅进“需报价”区；免费约赛该维预先标 N/A |
| 出行 Sᵣ | T 为需求明确允许的最长单程分钟数，t 为已核验方案的单程分钟数；`100×max(0,1−t/T)`。T=0 仅已确认无需出行时为 100；t>T 拒绝。缺路线/出发地不猜 t；时效依赖行程时先转待核验区 |
| 履约 S𝒻 | 最近 180 天中，n=已结案成功履约数+已判定服务方责任未履约数，c=成功数；n≥5 时 `100×c/n`，n<5 标样本不足。未决争议、客户撤单不计分母；团队仅用可核验约赛履约记录 |

每维输入、证据时间、公式版本、得分和缺失原因入快照；p、a、b、T 均以分钟并由客户明确给出，默认值须在审阅页展示。预算不适用的类型先从权重总量移除，不能与未知混同。覆盖度 C=已知维度权重/适用维度权重：C≥80% 为证据充足，50%≤C<80% 为有限证据，C<50% 仅放资料待补区；仅在相同证据档内按已知权重归一后的总分排序，不让少资料者凭高归一分挤掉证据充足者。公开评价只用已履约可核验记录，不用实名报名或私人聊天做特征。

同分使用需求固定种子的轮转；默认每 5 个展示位最多 1 个供合格新供给轮转，明确“新供给/样本不足”并保持证据分区，不能编造评分。按类型/城市记录曝光、联系与成交分布。用户能切换时间、出行、已确认总价排序；解释使用“档期覆盖”等事实，不能生成未经证实的“最佳/官方推荐”。评分版本冻结到一次结果，重新运行产生新版本。

## 4. 状态、数据与一致性

需求：`DRAFT → ACTIVE → PAUSED / CLOSED / EXPIRED`；暂停可恢复，关闭/到期后须复制为新需求。运行：`QUEUED → RUNNING → READY / FAILED / STALE`。意向：`PENDING → MUTUAL_INTEREST / DECLINED / WITHDRAWN / EXPIRED`；双方确认内容版本一致才进入 MUTUAL_INTEREST，再经显式预约操作进入 `CONVERTED`；一方改条件则原意向 `STALE`，名额已被其他意向转单则 `SUPERSEDED`。源订单仍执行其自己的接受、支付、取消与争议状态机。

需求发布时生成有限 `demand_slots`：TEAM_MATCHUP 只有一个对手席位；STAFF_SERVICE 按“岗位×数量”生成每人一个席位；ADULT_PLAYER 按“位置×数量×场次组”生成，每席位由一位成人球员覆盖指定整组 appearances，不把一人多场误算成多人。若各场允许不同人，创建不同场次组；同一实际用户不能占同组两个席位。场次/条件变化增加需求版本并重获意向确认，继续遵守 C06 单次最多 64 appearances 等限制。免费球队约赛无需预算；付费席位分别分配上限，合计不得超过需求总预算。

拟议新增表，不表示已有：

| 表 | 核心约束 |
| --- | --- |
| matching_needs | owner、组织范围、type、结构化条件、许可范围/版本、expires_at、version；类型专属字段 CHECK |
| matching_demand_slots | need_id、岗位/场次组、seat_no、预算上限、generation、state（OPEN/CONVERTED/SOURCE_ENDED）；need+岗位+场次组+seat_no 唯一；不是用意向数量推断人数 |
| matching_slot_assignments | slot_id、generation、intent_id、实际 user_id、source_ref、确认金额、源终态；slot+generation 唯一、source_ref 唯一；同需求/场次组/人员的有效指派唯一；追加历史不覆盖 |
| matching_runs | need_id、need_version、rule_version、seed、状态/失败码；同一需求版本/规则/请求键唯一 |
| matching_candidates | run_id、source_type/source_id、源版本、硬过滤证据摘要、评分/缺失维度；每运行每源唯一；不复制实名资料 |
| matching_intents | need_id、slot_id/generation、candidate_ref、双方确认版本、过期时间、status、source_ref；同需求/候选/席位代次/条件版本唯一；source_ref 唯一防重复转单 |
| matching_commands / outbox | actor_id+command_id 唯一、payload_hash、结果回执；事件类型+业务 id+version+接收人唯一 |

候选缓存和意向不占名额、不锁库存。转单必须在一个数据库事务中复查双方意向许可、源版本、实际地区、供给/资质、时间和价格，并锁需求行后原子将指定代次席位 OPEN 改为 CONVERTED、写 assignment；满额或该席位已占用就拒绝，不允许多意向分别通过 source_ref 唯一约束后超人数。同期复核席位和需求预算上限，再调用原 C06/X12 内部命令创建及锁位，最后写 source_ref 和 outbox；任一步失败全部回滚。禁止先 HTTP 创建再补记。源订单 REQUESTED 已占人数；转 ACCEPTED 不再扣一次。

新发意向同样锁需求行检查指定席位 OPEN；最后一席转出后阻止新意向/转换，并将该席位其余意向标 SUPERSEDED。源单取消、拒绝或过期只把席位标 SOURCE_ENDED，保留 assignment 历史、累计转单次数和金额，不自动恢复可用名额。用户明确执行 REOPEN_SLOT 后才核验源已终止、资源已释放且无未知退款/责任阻碍，增加 generation 并开放新一轮；旧意向不能复活。预算可用额=总上限−有效源金额−已结案仍由客户承担金额，待定退款不恢复额度；新增上限需客户明确重审。已履约完成不允许补位，关闭/到期需求须新建；源状态未知时保持不可用。C06 真实订单仍走原 REQUESTED/ACCEPTED，意向不能冒充服务方接受。

锁顺序沿用既有日历写路径：锁操作者 → 收集全部相关组织并按 id 排序锁 org_schedule_mutex → x12_calendar_lock → 按既有模块顺序的配额/命令锁 → C06 profile id 排序锁或 X12 资源/源行 → matching_needs → slots 按 id → intents 按 id。名额转换、源终态同步、补位均用此序；只写意向的事务按需求→席位→意向且不再获取源锁。不得在持有源行后补取组织锁。X12、C06 和 E04 共同验证；球员 30 分钟缓冲、工作人员缓冲及场地排斥约束保持。实施先核验源锁序，无法满足时回退原预约入口，禁止绕过锁。

重复 commandId 同载荷回放，异载荷 409；版本冲突返回重新审阅；超时显示“结果确认中”并查回执，不生成新命令重试。过期以数据库时间判定，后台清理只是加速，读写均做失效检查。

## 5. 拟议 API、迁移与安全

以下均未实现：`POST /v1/matching/needs`；`GET /v1/matching/needs/:id`；`POST /v1/matching/needs/:id/commands`（RUN/PAUSE/RESUME/CLOSE/REOPEN_SLOT）；`GET /v1/matching/runs/:id`；`POST /v1/matching/intents`；`POST /v1/matching/intents/:id/commands`（ACCEPT/DECLINE/WITHDRAW/CONVERT）；`GET /v1/matching/receipts/:commandId`。变更带 commandId、expectedVersion，服务端派生 owner/actor，不能由客户端指定对方确认状态。

迁移在现有 042 之后协调编号，先增表/索引/权限，不改历史订单语义，不回填全量公开许可；新功能默认关闭，机构/类型逐项启用。历史档案必须重新选择可被推荐地区、联系人和通知范围。迁移前验证当前 main 的最新号，不能预占 043。

TEAM_MATCHUP沿用X12有效的team_access_grants：双方的需求负责人和供给联系人都须获得对应球队管理授权；仅有机构所有者/管理员身份不能发布球队约赛需求、授权供给、接受或转换意向。授权撤销后候选及新写操作立即重新校验。成人球员及工作人员继续使用各自原业务权限。

权限按参与者、组织和具体动作判断，城市运营身份不等于跨机构明细权限；无权查询统一不可见。通知仅发需求编号、类型和站内入口，不携带私有姓名、电话、精确位置或未成年人名单；送达时重验接收权限。撤销公开/联系许可立即排除新候选、使未发送通知失效；既有订单依据订单权限保留必要快照。

恢复备份后默认 quarantine：暂停运行、转换和 outbox，重验权限、有效期、源订单映射及服务开关后人工解隔离；不恢复旧推荐为可预约事实。建议原始精确坐标只参与本次请求；需求保存经本人确认的服务地区，地址按参与阶段授权。候选缓存建议 24 小时失效；关闭需求的非必要候选明细建议 30 天清理，订单法定/业务留存另走现有策略。

## 6. 验收与拆包

以下为待执行验收，不能标记已通过：

1. 全国浏览无供给返回真实空态，不生成占位商家或可预约价格。
2. 用户仅许可本省时，后台重跑不能扩大到全国。
3. 已撤销发现许可、停用账号、审核失效的候选不出现。
4. C06 未满 18 岁档案拒绝，监护关系不能越过成人限制。
5. 无对应球队管理权、服务资质过期或实际地点越界均拒绝转换。
6. 档期表面空闲但与跨模块预约/30 分钟缓冲冲突时不可落单。
7. 未知报价分区提示；已知服务+交通+住宿+费用超预算不得宣称匹配。
8. 相同需求/规则输入可复现理由；缺履约数据无伪造星级。
9. 新供给有公平曝光且不会越过硬过滤；曝光不等于成交保证。
10. 双方只确认意向不创建已确认订单或触发支付。
11. 转换时价格、档期、覆盖范围或许可变化，整体回滚并要求重审。
12. 同一意向并发转单只产生一个源引用；同键异载荷返回冲突。
13. 响应丢失查回执恢复成功结果，不重复邀约和锁位。
14. 非参与机构、普通城市运营读取私有需求被拒绝；通知不泄漏详情。
15. 到期/撤回与接受并发只能产生一个合法终态；暂停需求不能新发意向。
16. 从旧备份恢复后无自动发信、扣款或转单，核验后才解除隔离。
17. 一个工作人员席位的两个意向并发转单只有一个成功；满额后禁止新意向，失败方不残留源订单。
18. 成人球员两名 PG、同组三场只生成两个席位；一人三次 appearance 不算三人，同人不得占两席，单场分组也按各岗位上限核验。
19. 源单 REQUESTED 已占名额，接受不重复计数；源取消不自动补位，用户重开生成新代次，旧意向不能再次转换。
20. 补位响应丢失/重复回调不会重复增席，历史指派和累计转单数保留；源状态未知或已完成禁止重开。
21. 两席并发确认时分别及合计不超过预算；源创建失败回滚人数和预算占用。

拆包：M1 契约/权限/表与功能开关；M2 分型资格过滤及证据快照；M3 版本化排序与公平曝光；M4 需求/候选/意向 UI；M5 C06/X12 原事务转换与 E04 接入；M6 隐私、并发、恢复测试和按城市灰度。M5 依赖源模块锁序与收费门槛验证；跨城工作人员自动分批邀约依赖独立派单设计，不能在本模块偷偷开启。完成标准包括可运行测试记录、真实角色操作记录和可关闭回滚开关。
