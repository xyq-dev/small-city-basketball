## 2. 共用业务规则

### 身份、授权与可见性

浏览范围、机构上下文、实际服务地点独立。全国发现只使用仍有效的公开发布资料；平台或城市运营身份不自动获得所有机构明细。成人球员预约沿用18+边界；培训、赛事监护授权按用途独立验证。需求、名单、保单、付款人、学生与收款方分别建模，不用一个userId承担全部角色。

用户明确触发的站内操作与通知分开；执行/送达前再次核验收件权限、订阅许可、内容版本与有效期。后台批处理不扩大联系范围，不向公开页面暴露电话、身份证、私人住址、医疗情况或未成年人完整名单。

### 同一日历、同一交易事实

撮合候选不是库存锁；意向确认不是订单接受。派单获得报价锁也不等于支付完成。培训锁名额与锁场地/教练分别管理，所有占用均需与赛事、球员和同城服务共用既有资源冲突规则。

实施前冻结统一锁序：相关组织按ID排序→既有共享日历互斥→各源既有命令/资源行锁→新域行；精确顺序必须根据当前C06/X12/E04写路径审计，不得按文档示意另起一套日历。过期、撤销、报价变更、付款回调与恢复任务都走同一约束。无法在同一事务满足时保留原入口，不拼接先HTTP创建后补记的半成品转单。

金额用整数分、币种明确；报价/协议/资格/费用版本随订单冻结。支付、退款、分账、承保等外部动作保持各自命令号、状态与原回执；`UNKNOWN`保留原号查询，不能通过换号重试或界面按钮制造第二笔事实。可执行动作由服务端当前capabilities决定，前端隐藏按钮不作为安全边界。

### 兼容、关闭与恢复

当前001—042迁移冻结；本文模型均为提案，实施时重新确认main后协调新迁移号。培训新的交易source kind、多方分账driver以及视野搜索DTO必须同时更新服务端、共享类型、消费者、权限、恢复和验收；不得只加界面。

开关按能力分离：发现/发邀约/新交易关闭时保留既有订单只读、退款核对和审计处理；关闭不能删除已存在资金/保单义务。备份恢复后对新任务默认quarantine，核验外部订单、签名凭据、租约代次和去重映射后再恢复。既有订单保持原合同快照，不追溯重算价格或分成。

## 4. 跨模块验收场景

1. 一名成人兼任裁判、球员和培训教练时，相同时段的不同来源并发预约只能留下合法占用；无权方只知冲突，不见他人订单细节。
2. 地图异地浏览后发需求，实际比赛地点须明确确认；浏览城市变化不改已冻结的服务地址、交通费或保险地域。
3. 供应商/人员撤销许可后，旧候选与未发送邀请失效；已成立订单按订单取消和保留规则处理，不删除资金证据。
4. 客户支付与派单锁/培训名额过期并发，不能超卖或占用别人的名额；外部已支付要核对后履约或退款，不抹掉回执。
5. 保险投保结果未知时，报名与培训UI不能显示“已保障”；退培训费与退保是两条相互关联但独立确认的事实。
6. 广告先分账后部分退款，退款、追回/可用余额和坏账记录守恒；不会通过重算旧协议侵占其他机构资金。
7. 恢复旧备份后，过期邀请、名额锁、支付命令、分账与投保不会自动重复发出；核对原外部编号再恢复。
8. 320/390/430手机和1440/1024后台宽度下，金额、时间、主要按钮与异常原因可读；截图/原型通过不替代接口、数据库或真机验收。
