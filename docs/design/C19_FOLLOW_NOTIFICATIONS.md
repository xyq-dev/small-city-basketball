# C19 关注后续通知草案（未实施）

2026-10-28；Agent 关注。状态：**草案，仅设计，不含代码、模板、凭据或后台任务**。本轮只交付关注/取消/我的关注/失效处理；没有调用任何微信发送接口，没有伪造模板、用户授权、送达结果或 worker。页面与接口始终把“关注成功”与“微信提醒未启用”分开表达（`FollowData.wechatReminder` 恒为 `NOT_ENABLED`）。

## 1. 启用前提（外部条件）

- 已审核的订阅消息模板 ID 与字段映射；小程序正式 AppID/secret 由运维注入，不入库、不入仓库。
- 用户在小程序内**针对具体模板**的一次性订阅许可（`wx.requestSubscribeMessage` 的 accept 结果），按“每次许可只可发送一次”记账；拒绝或未授权时不能显示“提醒已启用”。
- 发送通道、重试预算和监控由集成人另立任务卡审批；本文件不构成启用授权。

## 2. 数据草案

- `follow_notification_grants`：`(id, follow_id, user_id, template_key, granted_at, consumed_at, consumed_by_delivery)`。一次许可只可被一次投递消耗；取消关注或关注失效时剩余许可失效（不删除，记终态）。
- `follow_notification_deliveries`：一次通知意图一行。**去重键必须包含来源比赛身份**：

  `UNIQUE (follow_id, kind, source_publication_id, source_match_id, source_version)`

  - 不能只用 `followId + kind + sourceVersion`：同一赛事不同比赛的版本号彼此独立，可能相同（例如两场比赛都到达 version 7）。缺少 `source_match_id` 时，第二场的通知会被第一场“吞掉”。
  - 赛事级通知（如赛程整体发布）使用固定的 `source_match_id` 哨兵列或独立 kind，不能复用比赛级键。
  - `source_publication_id` 绑定公开发布：撤销后重新公开（新公开键）产生的事件不与旧发布的去重键混用，也不投递给旧关注（旧关注已 INVALID）。
- 运行时角色对两表无 DELETE；清理只置空负载列并记终态。

## 3. 发送前检查（每次投递、同一事务内锁定后检查）

1. 关注仍为 ACTIVE（未取消），且派生状态不是 INVALID：机构 ACTIVE、公开发布未撤销、赛事状态与用途匹配（与匿名公开读取同一闸门）。
2. 该次通知内容只取公开白名单字段（与 `/v1/public/events/*` 一致），绝不含私有 ID、联系人或已收回资料。
3. 存在一条未消耗、属于本人、模板匹配的订阅许可，并在同一事务内标记消耗。
4. 任一检查失败：投递记为 `SKIPPED_<原因>`，不发送、不重试。

## 4. 结果未知与重试

- 微信接口超时或连接中断属于**结果未知**：投递记为 `UNKNOWN`，不得盲目重发，也不得宣称“恰好一次”。
- 只有能确认未送达的错误（明确的参数/许可错误码）才可记为失败；可重试错误需在新的许可下以同一去重键重试，且重试前重新执行第 3 节全部检查。
- 对用户只显示“已尝试发送/结果待确认/已发送（以接口成功响应为准）”，不显示“已送达”。
- 投递 worker 若实施，须是有界、可观测、由维护脚本或明确部署的进程，不能描述为已在运行的无人值守服务。

## 5. 与本轮实现的接口关系

- 关注绑定 `public_event_publications.id`（`event_follows.publication_id`），失效由读取时派生；通知层不另存一份“有效”状态，避免与公开授权不一致。
- 页面入口：`pages/follows` 已有“关注与微信提醒分开”说明；启用后在此增加“开启本场提醒”按钮，按模板请求许可，并分开显示“关注中”与“提醒许可剩余次数”。
