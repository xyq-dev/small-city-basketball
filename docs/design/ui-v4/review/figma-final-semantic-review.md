# Figma V4 语义数据独立只读复核

范围：仅对照 `figma-final-screen-specs.json`、`figma-final-source-audit.md`、`remaining-ui-manifest-source.json`。未读取Windows未提交代码，未操作Figma或GitHub，未修改生成数据。以下结论针对当前设计数据的页面目的、角色和状态；不把“route存在”当作入口语义正确的证据。

## 必须修正

### 1. 同城“查看档期／可预约供给”错链到了本人预约订单页

- 位置：`local.sections[2].items[0].target = local-bookings`；`local.primary.target = local-bookings`。
- 当前按钮语义分别是球场“查看档期”、主操作“查看可预约供给”，目标 `local-bookings` 在当前及原始设计均是“我预约的／我提供的”原预约订单页，主视图已经有临时占档、待承接和原资金订单。
- 影响：用户尚未选择档期或发起预约就直接进入一个已有预约状态，跳过真实供给详情和预约提交，原型会混淆“找服务”和“查看原订单”。
- 修正：供给卡进入当前local页真实详情／档期／预约面板，必要时做同一路由的局部状态画面；若主操作仍要链接 `local-bookings`，文案必须改为“我的预约”，不能称“查看可预约供给”。不要凭空新增后端路由。

### 2. 球员中心“收到的预约”错链到了需求方预约清单

- 位置：`player-center.sections[3].items[1].target = bookings`。
- 当前及原始 `bookings` 定义是“本人需求方／我发出的球员预约”；`player-center` 承担本人服务档案和收到的预约。
- 影响：收件方操作进入发件方清单，混淆履约角色和可操作对象。
- 修正：保留球员中心现有收到预约的局部入口；如果实际代码确有received查询模式，必须连同明确模式和权限映射交接，不能仅靠无参数的 `bookings` route冒充收到的预约。

### 3. 平台两处管理入口目标画面与用途不符

- 位置：`platform.sections[2].items[2]` “城市授权管理” → `city-operations`；`platform.sections[2].items[3]` “评价处理” → `governance-reviews`。
- 当前 `city-operations` 是有限范围运营者查看本人授权范围和待办的工作台，不是授权签发编辑画面。当前 `governance-reviews` 的role为“真实完成订单参与人”，内容是本人填写评价并提交审核，不是独立平台审核评价。
- 影响：原型把授予城市权限和审核他人评价引向个人工作台／本人评价表，角色与任务不对应。服务端未必会越权，但导航会错误，不能据此称流程已串通。
- 修正：使用平台页现有受权管理面板／明确审核入口；实际面板未核对前移除这些错误直链，保留操作目的及权限说明，不把个人评价页当审核页。

### 4. 条件意向阶段的“原资金订单”入口需要存在性条件

- 位置：`booking-detail.sections[4].items[0]` “查看原资金订单” → `trade-order`。
- 当前展示的是条件意向，交通待核、最终费用未定，列表对应状态是资金未开始；审查边界明确意向不自动付款或成单。数据中没有本意向已建立原资金订单的证据。
- 修正：仅当服务端确有与该预约关联的原资金订单时显示此入口并传递原单上下文；本例默认应隐藏／禁用并说明“尚无关联资金订单”。不得让原型表现成意向自动生成收费单。真实订单存在时继续沿原单核对，不重建替代单。
