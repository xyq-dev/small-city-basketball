## 1. 公开赛事目录：补充决策

> **2026-10-28 更新**：本项已经审查，由 [C18](../tasks/C18.md) 按审定规则实现首版（Draft PR，未合并、未部署）。与下文不同之处：游标不做 HMAC，为未签名的结构游标（与筛选绑定；格式不合法、非规范编码或筛选不匹配返回 400，合法重编码的位置可能被接受，权限每次查询重新检查，游标不是授权）；匿名目录 `no-store`，不设 30 秒缓存。以 [方案“实施订正”](PUBLIC_EVENT_DIRECTORY.md#实施订正c182026-10-28) 为准，下文保留为送审原文。

已有方案已覆盖单独授权、前置条件、撤出、字段白名单、审计、表结构草案、API 草案与基本验收。还需拍板的决策：

- **状态推导**：只从现有字段推导，不新增比赛状态。
  - `LIVE`：赛事 RUNNING 且公开授权用途为 LIVE；
  - `UPCOMING`：SCHEDULED 且 LIVE；
  - `HISTORY`：COMPLETED/ARCHIVED 且公开授权用途为 HISTORY。
  - 其他组合不列出。
- **排序与游标**：
  - LIVE、UPCOMING 按 `startDate` 升序，HISTORY 按 `endDate` 降序，同序时按 `publicEventId` 排；
  - 游标只编码 `(status, sortDate, publicEventId)`，HMAC 签名、不可伪造，不含机构或赛事内部 ID；
  - 上架或下架导致翻页时允许漏项或重复，但不得越权。
- **城市字段**：`displayCity` 去空白后 1–20 字，只允许中文、字母、数字、空格与“·”；筛选为精确匹配，不做模糊搜索。
- **缓存与频率**：匿名目录 `Cache-Control: public, max-age=30`，撤出最长延迟 30 秒（需审查是否可接受；不可接受则改为 no-store）。同 IP 每分钟 60 次。
- **并发**：上架、下架命令走 `expectedEventVersion` CAS；“每个赛事至多一条 ACTIVE”用部分唯一索引保证。公开授权撤销与目录失效同事务。
- **Migration**：新增一张表、一个部分唯一索引，编号由集成人分配。
- **小程序**：
  - watch 页增加“公开赛事”分区（匿名可读，分页），点击进入现有 event 页；
  - event-setup 公开观赛卡增加“列入目录 / 撤出目录”（4–500 字原因）；
  - 撤出后再次刷新，条目即消失。
- **补充验收**：
  - 游标篡改返回 400；（C19 订正：实际实现为未签名结构游标，只保证格式不合法、非规范编码或筛选不匹配时返回 400，合法重编码的位置可能被接受；权限来自每次查询的有效公开条件。）
  - 撤出后缓存窗口内的读取行为与审查结论一致；
  - `displayCity` 非法字符被拒；
  - 同一赛事并发上架只成功一次。

## 3. 球员自建 / 自主加入球队：补充决策

C14 §2 已有业务规则、表、API 与权限草案。还需拍板的决策：

- **申请状态机**：
  - `PENDING → APPROVED | REJECTED`，或由申请人撤回 `PENDING → WITHDRAWN`；
  - 只有 PENDING 可审；
  - 审核须 4–500 字原因并做 CAS，审核人不得是申请人。
- **加入码**：
  - 128 位随机，展示 Base32 共 26 位，只存 SHA-256；
  - 默认 7 天、最多 30 次；
  - 校验失败按账号与 IP 限流（每分钟 10 次）。
- **幂等与并发**：
  - 同一账号重复加入同一球队，返回现有绑定，不再计次；
  - 计次用 `UPDATE … SET used_count = used_count + 1 WHERE used_count < max_uses AND revoked_at IS NULL AND expires_at > now() RETURNING`，并发下不超发。
- **绑定与名单**：
  - 绑定只关联“成员记录 ↔ 账号”，不改变已冻结的报名快照；
  - 未绑定的成员照常可报名；
  - 绑定后，球员预约与数据授权可识别本人。
- **隐私**：领队只能看到绑定账号的显示名，看不到邮箱。
- **Migration**：三张表（申请、绑定、加入码）。
- **补充验收**：
  - 加入码用尽的并发边界；
  - 被移除后重新加入；
  - 申请人不能审核本人申请。

## 4. 跨届 / 赛季球员数据：补充决策

C14 §3 已定只聚合授权记录、未采集项目显示“未统计”。还需拍板的决策：

- **赛季实体**：`seasons(org_id, name, starts_on, ends_on, status DRAFT|ACTIVE|CLOSED, version)`。
  - 赛事按 `startDate` 自动归入赛季，或由管理员显式指定（二选一，建议显式指定，避免日期边界歧义）。
- **聚合主键**：只用第 3 项的成员—账号绑定；未绑定的成员不跨届合并。
- **重算规则**：
  - 读取时按 `sourceHash` 重算或命中缓存；
  - 撤销授权、重开赛果后，下一次读取即剔除；
  - 不另建第二套赛果。
- **API**：
  - 私有：`GET /v1/orgs/:o/seasons`、`GET …/seasons/:s/player-statistics`；
  - 公开榜单另需授权命令（与公开观赛同等白名单），**本项首期不做公开**。
- **Migration**：赛季表，以及赛事与赛季的关联列或关联表。
- **补充验收**：
  - 跨机构不合并；
  - 赛季关闭后数据只读；
  - 授权撤销即时生效。

## 5. 关注与提醒：补充决策

C14 §4 已定只对公开赛事、用户主动订阅的事件发送。还需拍板的决策：

- **订阅模型**：`event_follows(user_id, public_event_id, kinds[], created_at, revoked_at)`。只能关注目录中或已打开过的公开赛事；授权失效时订阅同步失效。
- **发送幂等**：发送记录以 `(follow_id, kind, source_version)` 唯一，重试不重复发送。微信订阅消息需逐次授权，未授权一律不发。
- **外部前置**：在已提供的 AppID 下申请订阅消息模板，服务端配置发送凭据与配额。缺少这些时功能不开放。
- **Migration**：订阅表、发送记录表。
