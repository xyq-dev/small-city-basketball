# 多 AI 协作与持续更新

适用范围：Codex、Claude Code 和其他经用户授权的协作者。本文规定工作方法，不创建新账号权限或发布授权。

## 1. 协作角色

| 角色 | 责任 | 写入范围 |
|---|---|---|
| 用户 | 目标、业务取舍、费用与高影响操作授权 | 最终决定 |
| 集成人（每轮只设一位） | 拆任务、确认认领、整合、更新 main 事实 | 汇总文档、共享契约、整合结果 |
| 实施 AI | 按既定方案实施和验证，发现关键冲突先反馈 | 分配的代码路径及自己的任务/交接记录 |
| 审查 AI | 按风险独立检查实现与证据 | 审查记录；不自动取得修改或合并权限 |

当前文档任务集成人为本次 Codex 会话。后续集成人在会话启动时明确记录；此标记不是永久独占。

## 2. 唯一事实入口

- `CURRENT_STATUS.md`：main 的已整合事实；基线必须附 SHA 和核验日期。
- `TASKS.md`：任务总览；任务详情放 `tasks/<ID>.md`，验证和接续放 `handoffs/<ID>.md`。
- `DECISIONS.md`：关键决策和未决事项；不要在多个任务内各自发明相反结论。
- GitHub 分支/PR/提交用于共享代码和证据。聊天结论须落入相应文档，聊天历史不能替代当前工作区核验。
- 当事人更新任务记录不等于 main 已完成；“分支已验证”“已提交未合并”“main 已整合”“线上已验证”必须分别写清楚。

## 3. 认领与并行

1. 集成人先确认任务依赖、唯一负责人、基线 SHA、任务分支、允许路径、共享文件和权限。
2. 负责人将卡片从 TODO 改为 IN_PROGRESS，记录 AI/会话标识、开始时间与当前检查点。只有集成人确认认领后才进入写入。
3. 使用独立 checkout/worktree；已有未提交工作先保留并记录，不能由另一个 AI 换分支接管。
4. 两个 AI 不得同时写同一业务文件或同一任务卡。需要共享契约或锁文件变更时，交由该文件负责人先整合，再让其他任务同步。
5. `CURRENT_STATUS.md` 与 `TASKS.md` 由集成人单写；各实施 AI 只更新自己任务和交接记录，再报告集成人更新汇总。
6. 本流程不是分布式锁。发现重复认领、并发分支更新或路径冲突，停止重叠写入，由集成人裁决；不能用 force push 或“最后一次写入”解决。
7. 负责人失联不自动释放任务。记录最后检查点，由集成人显式重分配；新负责人先检查原分支与未提交成果。

## 4. 必须触发更新的时点

| 时点 | 负责人需写入的内容 |
|---|---|
| 开工 | 目录、远端、分支、HEAD、dirty、负责人、允许路径、权限、计划验证 |
| 活跃工作每30分钟或有实质进展 | 完成到哪、变化文件、最后可恢复点、尚未验证项 |
| 需求/数据/API 改动 | 变更原因、契约版本、消费者影响、相关规范与依赖任务 |
| 受阻 | 具体错误、已尝试操作、可保留成果、解除条件；状态 BLOCKED |
| 验证完成 | 实际命令、环境、结果、提交/工作区依据及失败项 |
| 交接/结束会话前 | 已做/未做、未提交文件、下一条具体操作、风险和授权边界 |
| 合并或 main 更新后 | 集成人更新任务看板与状态，记录最终提交；不得复制未核验的分支结论 |

记录使用带时区的 ISO 时间或明确的 Asia/Shanghai 日期。不能用“刚刚”“上一版”“都通过了”等不可追溯表述。未发生事件不制造心跳；AI 停止运行不会持续写入。

## 5. 任务状态

`TODO → IN_PROGRESS → REVIEW → DONE`。`BLOCKED` 可从执行或审查进入，解除后回到原阶段；`CANCELLED` 需记录原因。

- TODO：待认领或依赖未就绪。
- IN_PROGRESS：正在实现，不代表可以发布。
- REVIEW：范围已实施，等待必要验证、审查或整合。
- DONE：验收证据齐全且达到任务规定的交付状态；需要 main 整合的任务必须已整合。
- BLOCKED：有明确不能继续的依赖或环境问题。

任务还应单列 `integration`：`LOCAL_ONLY / BRANCH_ONLY / MAIN`，以及环境验证范围。不要把提交成功、CI 通过和生产可用混为同一状态。

## 6. Git 与文档同步

1. 每次写入前核验远端和当前分支，不假设 main 没变。
2. 后续业务变更走任务分支和 PR；文档整理由集成人在明确授权范围内同步。用户本次要求建立并持续更新的项目文档可以同步至此仓库，但不附带业务代码发布权限。
3. 只暂存明确列出的文件，不混入其他任务。多个任务修改根配置、依赖锁或共享契约时由集成人串行整合。
4. 分支或 GitHub API 更新须基于读取到的 HEAD；发生并发冲突重新读取并整合，禁止强制覆盖。
5. 文档优先随对应代码一起提交。代码尚未获准提交时，本地任务记录写明未提交范围；只有得到代码同步授权后才推送代码。
6. 远端不可达或没有写入权限时，保存本地记录、标记“未同步”并交付具体路径/提交，不能声称其他 AI 已能读取。不要自动创建无人值守任务或要求用户重复授权既有范围。

## 7. 接口或设计冲突

记录冲突位置、现有行为、目标规则和受影响任务。先暂停依赖冲突部分；不依赖该结论的工作可以继续。普通实现选择由负责人在任务范围内决定；涉及跨机构访问、计分一致性、资金、数据库迁移或生产影响时，由集成人完成必要审查后再推进。

## 8. 最小完成记录

每次交付必须包含：任务 ID、负责人、实际上下文、变化文件、验收逐项结果、未执行验证、未决风险、Git 及远端状态、Migration 编写/执行状态、下一位 AI 的第一条操作。格式见[交接模板](handoffs/TEMPLATE.md)。

当前没有自动文档同步服务。P01已本地编写应用CI工作流，尚未提交或远端运行；未配置CI文档门禁。[PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)提供检查项；实施 P01 时再增加与实际工具匹配的 CI，不能把模板勾选当作已经执行验证。
