### 1. 分组与淘汰赛

- **排赛页（schedule）扩展到三种赛制**：单循环 `RR_CIRCLE_V1`、单淘汰 `SE_SEEDED_V1`、分组 `GK_BALANCED_V1`（分组数按“每组至少2队”给出可选项，种子队每组至多一支，`groupConfig` 原样提交）。生成后显示服务端回放的分组结果、单淘汰首轮轮空队；重抽沿用原 `groupConfig`。分组赛发布前须锁定组内积分规则（服务端 `STANDINGS_RULES_REQUIRED`），页面提前说明并直达规则设置。
- **赛事设置（event-setup）**：积分规则与公开观赛对三种赛制都读取，是否可编辑完全按服务端 capabilities（单淘汰无积分规则，只有公开观赛）。分组赛标题为“组内积分规则”。
- **新页 bracket（分组积分与晋级）**：
  - 组内积分表、出线顺序、同分待抽签球队、已保存抽签记录（顺序、原因、时间）。
  - 同分抽签：需4–500字原因，固定提交该组 `standings.sourceHash` 与赛事版本；只保存一次。
  - 淘汰轮次：每轮显示是否已发布；每个签位显示对阵或“待定（来源胜者）”、轮空晋级、比赛状态、胜者；点开进入单场；完赛后显示最终名次。
  - 发布：资格首轮 `PUBLISH_QUALIFICATION` 与后续轮 `PUBLISH_ROUND`。逐场选场地、日期、北京时间，并填写原因；提交时固定读取到的 `sourceHash` 与赛事版本。冲突逐项显示。发布会撤销实时观赛链接，页面提示须重新开启公开观赛。
  - 不可操作原因按服务端状态与 capabilities 显示：等待组赛确认、需抽签、无权限、等待本轮确认。
  - 来源赛果变化：服务端 409 时保留已填安排与原因并重新读取。重读时如发现 `sourceHash` 已变，提示“来源赛果已变化，请重新核对”，下次提交使用新 hash。
  - 响应丢失：不自动重发，必须重新读取核对后才能继续。
- 入口：赛事详情（org-event）管理卡“分组积分与晋级发布 / 签位与下一轮发布”；排赛页发布后同名按钮。

### 2. 正式比赛改期

- **新页 reschedule**：
  - 显示当前正式安排、原排赛时长、改期历史（最近20条，from → to、原因、时间）。
  - 场地只列可用场地；日期与北京时间选择器；原因1–500字。提交 `RESCHEDULE`，携带赛事与比赛版本。
  - 冲突明细按“本场 / 与同届其他比赛 / 本机构其他赛事”显示；`RESCHEDULE_UNCHANGED`、`MATCH_CANNOT_RESCHEDULE` 等有对应说明。
  - 版本冲突时重读，并保留已填内容。
  - 响应丢失时不自动重发，须重读核对。
  - 不能改期时说明原因：比赛已开始或结束、赛事已关闭、身份不足。
- 页面明确这是对已发布比赛的正式改期而非排赛草稿；原发布快照不变，每次改期单独记录。真实联调中核对过：改期后赛程发布记录仍在。
- 入口：单场详情（org-match）“比赛管理 → 正式改期”，仅比赛为 SCHEDULED/READY 时显示；赛事详情 → 赛程 → 单场。

### 3. 比赛媒体

- **新页 match-media**：
  - 机构额度与单文件上限：8 MiB，来自服务端 usage。
  - 选择图片（PNG/JPEG）或视频（MP4）：`wx.chooseMedia`，旧客户端退回聊天文件选择。读取与发送前先在本地检查类型、大小和额度。
  - 上传分阶段显示：读取 → 上传 → 已私有保存（见“未完成”中的进度说明）。
  - 失败处理：
    - 已知失败：保留原文件，可“按原文件重试”。
    - 响应丢失：结果保持“未知”（见下方“PR #24 媒体审查修复”）。现有接口没有请求编号，不能自动判定，也不允许重试或新上传；由组织者人工核对后结束。
  - 媒体流转：文件 → 创建草稿（标题＋4–500字权利声明，类型按文件用途）→ 发布（仅有发布权限者）→ 撤销。另可撤销私有文件（4–500字原因）。
  - 状态文案：
    - 文件：“已私有保存 · 未关联、未发布”或“已关联媒体”。
    - 媒体：“草稿 · 未公开”“已发布 · 公开观赛开启时观众可见”“已撤销 · 不再公开”。
  - 媒体的公开范围仍只经由本届公开观赛授权。
- 上传请求单独使用 120 秒超时（`utils/api.js` 的 `request(..., timeout)` 仅媒体上传传入，范围 8–120 秒）；其他请求仍为 8 秒。
- 入口：单场详情“比赛管理 → 比赛媒体”。

## PR #24 媒体审查修复（2026-10-27）

本节修正上文的旧说法：现有接口**不保证**重复请求只保存一份。本轮实现的是“安全保留未知结果”，**不是**幂等恢复。

- **选择器绑定原账号与页面**：打开选择器前固定会话令牌（`ui.guard`）、操作序号和当前账号。选择器返回后，先核对原操作是否仍有效、当前是否仍有上传能力，然后才读取或提交。
  - 退出、切换账号、页面卸载后，迟到的选择结果直接丢弃：不读取文件，也不上传。
  - `ui.hold` 只用来取消进行中的读取；有效性始终绑定选择前的令牌，不会用新令牌接纳旧操作。
- **未知结果不再靠弱匹配解除**：删除了按同名、同大小、两分钟时间窗判定成功的逻辑。
  - 上传或草稿创建前，先把记录写入本机存储，按账号、机构、比赛区分，最多保留 20 条。
  - 响应未知时保持“未知”，单次刷新没找到不等于失败。
  - 在此期间不能重试、不能重新选择文件、不能创建草稿；退出再进入页面也保留。
  - 重读后，把该次操作之后出现的同名同大小文件（或引用同一文件的草稿）列为候选，明确写“系统不作证明”。
  - 只有组织者点“是这一份”（结果显示“由你核对确认”），或经确认提示“结束此记录”，才会结束。
- **已知失败**（有状态码的拒绝）仍可按原文件重试。发布与撤销有版本校验，未知结果重读即可，沿用原逻辑。
- **完整自动恢复**需要请求幂等接口，方案见 [C15_MEDIA_IDEMPOTENCY_PROPOSAL](../design/C15_MEDIA_IDEMPOTENCY_PROPOSAL.md)（待审，本轮未改后端）。

## 未完成 / 待审 / 依赖（不把“有入口”算完成）

- **媒体上传/草稿创建没有请求幂等**：响应丢失只能安全保留为未知并人工核对，见上节与待审方案。

- **媒体子功能未原生**：时间标记（markers）、外部链接媒体（需受信主机配置）、内容清除（purge）、私有文件预览。媒体若带时间标记且赛果已重新确认，页面会提示“标记待更新”，但不能在小程序重建。
